<objective>
Lay the irreversible foundation and prove the whole pipe works end-to-end: a Cargo workspace (`agent-memory-core` lib + `agent-memory` bin), the SQLite store (schema, WAL, single-writer, FTS5 mirror created up front), typed memory CRUD for store+list, and an rmcp stdio MCP server exposing `memory_store` and `memory_list`. The walking skeleton is: an MCP client pipes `initialize` then `tools/call memory_store` then `tools/call memory_list` and gets a valid id back and the row back, over real stdio and real on-disk SQLite, with the data surviving a restart and nothing but JSON-RPC ever reaching stdout.

This plan also lands ALL Wave-0 test harness scaffolding (clock injection, the store integration test, and the binary-spawning stdio/tools tests) so Plans 02 and 03 inherit an automated feedback loop.

Purpose: This is the Walking Skeleton for a greenfield project. The hard-to-retrofit decisions (stdout purity, WAL + single-writer, injectable Clock/UTC, decay≠delete schema separation) are locked here once.
Output: A buildable, testable workspace where `memory_store` + `memory_list` work over MCP stdio against durable SQLite.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| MCP client → server (stdin/stdout) | Untrusted tool-call arguments (`content`, `type`, `tags`, `scope`, `ttl`) cross here as JSON-RPC |
| server → SQLite file | Persisted memory content; file lives in a shared OS data dir readable by other local users unless restricted |
| server → stdout | The JSON-RPC channel; any non-protocol byte corrupts the client (a DoS of the session) |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
