Then ship the phase: the self-hosted-runner CI workflow (fmt, clippy, test, stdout-purity, >80% coverage gate) and a README so v0.0.1 is releasable in shape.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| background sweep → SQLite writer | The sweep deletes/updates rows; a bug here could destroy non-expired data |
| sweep logging → stdout | The sweep runs concurrently with serving; its log output must never reach the JSON-RPC channel |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-01 | Tampering / data loss | sweep DELETE scope | mitigate | `sweep_expired` is the ONLY delete; bound `WHERE expires_at IS NOT NULL AND expires_at < ?1`; decay materialization is structurally UPDATE-only (cannot DELETE) — STORE-04 invariant asserted by `tests/ttl.rs` |
| T-03-02 | DoS | sweep log → stdout corruption | mitigate | SweepReport logged via `tracing` to stderr only; `stdio_purity.rs` re-runs with the sweep active to prove stdout stays pure |
| T-03-03 | DoS | writer contention from sweep + stores | mitigate | Single serialized writer lane + WAL + `busy_timeout` (Plan 01); sweep is one short transaction per interval, not per-row locking |
| T-03-SC | Tampering | crates.io / CI toolchain | mitigate | `cargo install cargo-llvm-cov` is a pre-audited dev tool (RESEARCH §Package Legitimacy, OK); CI pins `dtolnay/rust-toolchain@stable`; runs only on org self-hosted runners |

No HIGH-severity threat is left unmitigated.
</threat_model>
