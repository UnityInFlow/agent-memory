# Plan 04-06: Gap Closure — Write-path integrity (backfill race, symmetric relates_to)

## Phase Goal

**As an** agent, **I want to** update existing memories, link related ones, and get hybrid keyword+semantic recall, **so that** my memory stays **current and connected** and I find the right memory even when the phrasing differs.

This plan makes "current" and "connected" hold under concurrency:

- an edited memory can no longer be silently re-embedded with its OLD text by a backfill that was already in flight (REVIEW CR-03);
- the symmetric `relates_to` relation can no longer be stored twice and expanded twice (REVIEW WR-03).

<objective>
1. **CR-03.** Make the sweep's embedding backfill conditional. A vector is written only if the row is still pending AND its content still equals the text that was embedded. The check is one guarded UPDATE in the same writer transaction as the vector write. This closes three races:
   - update-vs-backfill;
   - forget-vs-backfill;
   - sweep-vs-sweep across the several processes that share one DB file.
2. **WR-03.** Store `relates_to` canonically as (min id, max id), and let unlink remove a symmetric edge from either end. Directed kinds are untouched.
3. **IN-05, IN-06 and WR-04.** Document three existing behaviours, with no behaviour change:
   - an update on an expired-but-unswept row succeeds;
   - a snippet may split a grapheme cluster;
   - an expanded `memory_list` without a limit returns every row. This corrects the `MAX_EXPANDED_LINKS` doc's 200 × 10 claim; WR-04's behaviour change is deferred.

Purpose: MCP-06's success criterion 1 ("the old meaning no longer matches semantically") and MCP-07's flat-relation idempotency (D-02) must hold when writers interleave, not only when they run serially.
Output:
- the conditional `Store::insert_embedding`;
- the sweep wiring;
- relates_to canonicalisation;
- deterministic race tests and relations tests;
- updated docs.
</objective>

## Interface contracts (established by this plan)

- `Store::insert_embedding(&self, memory_id: i64, expected_content: &str, embedding: Vec<f32>) -> Result<bool, MemoryError>`. This REPLACES the old `(memory_id, embedding) -> Result<(), _>` signature. Its only caller is `MemoryService::sweep`; there are no other `Store` implementors.
  - `Ok(true)`: the vector was written and `embedding_status` became 1.
  - `Ok(false)`: nothing was written, because the row was updated, already embedded, or forgotten since `pending_embeddings` read it.
  - The claim is a single guarded `UPDATE memories SET embedding_status = 1 WHERE id = ?1 AND embedding_status = 0 AND content = ?2`, run FIRST inside the writer transaction.
  - Zero changed rows → return `Ok(false)`; the transaction rolls back on drop.
  - Otherwise, `DELETE` + `INSERT` the vec0 row in the same transaction (never `INSERT OR REPLACE` on vec0, per the v1.0 decision), then commit.
  - SQLite takes the write lock at that UPDATE statement, so the claim is atomic across processes as well as across threads.
- `LinkKind::is_symmetric(self) -> bool`: true only for `RelatesTo`.
- `LinkKind::canonical_endpoints(self, from_id: i64, to_id: i64) -> (i64, i64)`:
  - `RelatesTo` → `(min, max)`;
  - `Supersedes` and `CausedBy` → `(from_id, to_id)` unchanged.

  Both use exhaustive matches with no `_` arm.
- Canonicalisation is invisible on the wire. Every `memory_link` / `memory_unlink` response and REST link body echoes the REQUEST's `from_id` / `to_id`: the `{from_id, to_id, kind, linked|unlinked, ...}` body and the not-found body with `missing_id`. Transports build those bodies from the request, never from the stored row. `LinkOutcome` carries no endpoint ids besides `missing_id`, and that is a request id.
- `SqliteStore::link` checks both endpoints in REQUEST order, exactly as today, so `LinkOutcome::NotFound { missing_id }` keeps naming `from_id` first. Only then does it INSERT OR IGNORE the canonical pair.
- `SqliteStore::unlink` deletes `(from_id, to_id, kind)`. For a symmetric kind it also deletes the reversed orientation, which covers canonical rows and any relates_to row written by a pre-fix dev build of the unreleased 0003. No migration is involved, and 0001/0002/0003 SQL is untouched.
