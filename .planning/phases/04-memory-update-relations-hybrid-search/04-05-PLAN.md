# Plan 04-05: Gap Closure — Forgiving keyword leg (natural-language queries never fail search)

## Phase Goal

**As an** agent, **I want to** update existing memories, link related ones, and get hybrid keyword+semantic recall, **so that** my memory stays current and connected and **I find the right memory even when the phrasing differs**.

This plan closes the search slice of that story. Today, with Ollama up, every query must parse as FTS5: a question mark makes search fail with invalid_params, and a hyphen (`sqlite-vec`) makes it fail with a 500 that leaks SQLite text. After this plan, an agent can ask in plain language, with any punctuation, in either mode, and get the right memory back.

<objective>
Implement the locked user decision **option-a (sanitize & retry)** at the one store seam both search paths share, and redact every search-path failure at the service seam.

- The raw query runs first, so valid structured FTS5 syntax keeps its meaning.
- If FTS5 rejects the raw query as client input, the query is retried ONCE, with its word tokens quoted and OR-joined. The client-input classes are `fts5: syntax error`, `unterminated string`, the step-time `no such column` class from hyphens and colons, and the three further FTS5 parse classes found during planning (`unknown special query`, `expected integer`, `fts5: parser stack overflow`).
- A query with no word tokens adds nothing from the keyword leg.
- Any failure left over after the retry, and every internal search error, reaches the client only as a generic internal message.

Purpose: restore paraphrase recall for punctuated agent questions (VERIFICATION truth #15), remove the hyphen/colon 500 and its SQLite-text leak (truth #14, CR-01), and keep T-04-15's "same classification in every mode" property (CR-02).
Output: a forgiving keyword leg, a search-path redaction point, the old 400-pinning tests reversed, two-mode decision tables at the core and on both transports, and docs that match.
</objective>

## Locked user decision (2026-10-23, resolves VERIFICATION human_verification #1 and REVIEW CR-02)

**option-a — sanitize & retry.**

1. The raw query runs through FTS5 first.
2. If FTS5 rejects it as client input, the query is retried ONCE with its tokens quoted and OR-joined.
3. If nothing tokenizes, the keyword leg contributes nothing. Hybrid returns semantic-only results; keyword mode returns an empty set, not an error.
4. The classification is identical with Ollama up or down.
5. The step-time `no such column` 500 is eliminated.
6. A raw SQLite message never reaches a client on any search path.
7. The tests that pin the old 400 behaviour are reversed.

RESEARCH's degrade-table row "InvalidQuery from keyword leg → propagate → 400 in ALL modes" (04-RESEARCH.md §Pattern 1) and the 04-04 must-have "A malformed MATCH query is a 400/invalid_params in hybrid mode" are **superseded** by this decision. Honor this decision, not those.

## Interface contracts (established by this plan)

Private helpers in `crates/agent-memory-core/src/store/sqlite.rs`:

- `fn is_match_input_error(e: &rusqlite::Error) -> bool`
  - True only when both hold:
    - the error is `rusqlite::Error::SqliteFailure` with primary result code `SQLITE_ERROR` (`extended_code & 0xff == rusqlite::ffi::SQLITE_ERROR`);
    - the message contains one of the FTS5 query-parse markers: `fts5: ` (covers `fts5: syntax error near …` and `fts5: parser stack overflow`), `unterminated string`, `no such column`, `unknown special query`, `expected integer`.
  - It is only ever handed errors raised AFTER the static statement prepared, so a `no such column` there can only come from FTS5 parsing a column filter out of the MATCH string.
- `fn sanitize_fts_query(raw: &str) -> Option<String>`
  - Splits on every char that is neither `char::is_alphanumeric` nor `_`.
  - Drops empty pieces and wraps each piece in double quotes. Any embedded `"` is doubled defensively, though none can survive the split.
  - Joins the pieces with ` OR `, preserving order, with no dedupe and no cap.
  - Returns `None` when no piece remains.
- `fn match_with_sanitized_retry(raw: &str, run: impl FnMut(&str) -> Result<Vec<MemoryView>, rusqlite::Error>) -> Result<Vec<MemoryView>, MemoryError>`
  - `run(raw)` succeeds → its rows.
  - `run(raw)` fails with `is_match_input_error`, then:
    - `sanitize_fts_query(raw)` is `None` → `Ok(vec![])`;
    - `sanitize_fts_query(raw)` is `Some(f)` → `run(f)`, and ANY error from that retry is `MemoryError::Sqlite`. That is a server fault: the retry parses by construction.
  - `run(raw)` fails with any other error → `MemoryError::Sqlite`.

Public in `crates/agent-memory-core/src/service.rs`:

- `pub const SEARCH_STORAGE_FAILURE: &str = "search failed due to a storage error (details are in the server log)"`.
- `fn redact_search_error(e: MemoryError) -> MemoryError`. This is the only place search errors are tiered for the wire.

Probe results that drove the marker list, from the system sqlite3 3.46 CLI against `fts5(content)`. The bundled 3.51.3 is the source of truth, and Task 2's unit test pins it.

| query | FTS5 result |
|---|---|
| `what vector store do we use?`, `don't retry`, `auth, tokens`, `C++`, `AND`, empty, `?!,`, `a.b`, `C#` | `fts5: syntax error near …` |
| `sqlite-vec`, `auth: tokens`, `re-embed`, `x86-64`, `TODO: auth`, `-a` | `no such column: …` |
| `"unbalanced`, `"` | `unterminated string` |
| `*`, `*a` | `unknown special query: …` |
| `NEAR(a b, x)` | `expected integer, got "x"` |
| 3000-deep `(`…`)` | `fts5: parser stack overflow` |
| `"exact phrase"`, `sqlite AND vec`, `vec*`, `content: tokens`, `""` | valid (runs raw) |

A 20,000-term quoted OR chain parses and runs in about 0.2 s, so the retry needs no token cap.

**Shared test corpus.** Every decision-table test in this plan uses the same five PATTERN memories, so expectations are identical across layers:

- M1 `We chose sqlite-vec for local vector similarity search`
- M2 `auth tokens rotate every hour`
- M3 `C++ build flags need care`
- M4 `don't retry the import blindly`
- M5 `the unbalanced ledger is reconciled nightly`

**Decision table.**

| query | expected top hit, keyword AND hybrid mode |
|---|---|
| `what vector store do we use?` | M1 |
| `sqlite-vec` | M1 |
| `don't retry` | M4 |
| `auth, tokens` | M2 |
| `auth: tokens` | M2 |
| `C++` | M3 |
| `"unbalanced` | M5 |

Tokenless or no-hit queries: `AND`, the empty string, `?!,` and `*`.

- In keyword mode they return an empty result set. `AND` sanitizes to the phrase "and", which no corpus row contains.
- In hybrid mode they return a non-empty, semantic-only result set.

Every row is `Ok`, carries the mode's `search_mode`, and has no `sqlite error` text in any response body.
