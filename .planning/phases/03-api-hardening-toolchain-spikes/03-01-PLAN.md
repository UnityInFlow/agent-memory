# Plan 03-01: Validation Seam + Exact Tag Matching (API-02 + API-03)

## Phase Goal

**As an** agent or REST client, **I want to** have invalid inputs rejected cleanly at one shared seam and tag filters match tags exactly, **so that** bad requests never surface as server faults or over-matched results on any transport.

This plan delivers the whole code-hardening slice of that story: out-of-bounds `limit`/`ttl_secs` reject as descriptive client errors at the `MemoryService` seam on both transports (API-02, D-01..D-06), and `tag=rust` stops matching `rustling` on all three query paths (API-03, D-07..D-09). The toolchain-spike slice is plan 03-02.

<objective>
Implement API-02 and API-03 as one vertical hardening slice over the shipped v0.0.1 codebase:

1. **Validation seam (API-02, D-01..D-06):** add `MemoryError::InvalidArgument(String)` (D-04) plus `pub` bounds consts (D-03: `MIN_LIMIT=1`, `MAX_LIMIT=200` per D-01; `MIN_TTL_SECS=1`, `MAX_TTL_SECS=3_155_760_000` per D-02) and two shared validation helpers in `agent-memory-core`. Validate at the top of `MemoryService::{store, search, list, import}` (D-06 — one seam, both transports inherit; `import()` is included because it bypasses `store()`). Remove the silent `.max(0)` clamp at `service.rs:168` (D-01). Both exhaustive error mappers gain the new client-tier arm (D-04), and the message shape is field + range + offending value (D-05: `invalid argument: limit must be between 1 and 200 (got 0)`).
2. **Exact tag matching (API-03, D-07..D-09):** replace all three `tags LIKE '%' || ? || '%'` predicates in `sqlite.rs` with `json_each` equality EXISTS predicates (D-07), case-sensitive whole-tag semantics (D-08), locked by a per-site regression fixture (D-09), with the four agent-facing doc strings and the README updated in the same plan.

Discretion resolved (per CONTEXT "Claude's Discretion"): `deny_unknown_fields` is NOT added this phase — it would be a third behavioral change and keeps the v0.1.0 release-notes delta to exactly the two decided changes (RESEARCH Open Question 2). Bounds consts live in `domain.rs` beside `MemoryError` (RESEARCH recommendation). Cargo.toml is untouched — zero new dependencies.

Purpose: flip Phase 3 success criteria 1-3 to true; every later v1.1 surface (update/link/export/import) routes new inputs through this seam as it lands.
Output: one error variant, four consts, two helpers, four validated service methods, three exact-match SQL predicates, both mapper arms, four doc-string fixes, README contract docs — all locked by the 02-05 four-layer test template.
</objective>

## Interface contracts (established by this plan — Phases 4-5 consume these)

- `crates/agent-memory-core/src/domain.rs` exports, all `pub`:
  - `MIN_LIMIT: i64 = 1`, `MAX_LIMIT: i64 = 200` (D-01; `MAX_LIMIT` == the KNN cap so a valid limit never exceeds what the KNN leg honors)
  - `MIN_TTL_SECS: i64 = 1`, `MAX_TTL_SECS: i64 = 3_155_760_000` (D-02; `now + MAX_TTL_SECS` is far below `i64::MAX` — overflow unreachable)
  - `MemoryError::InvalidArgument(String)` — client tier, thiserror display `invalid argument: {0}`
- Validation helpers (`pub(crate)`, in `domain.rs`): `validate_limit(Option<i64>) -> Result<(), MemoryError>` and `validate_ttl(Option<i64>) -> Result<(), MemoryError>`; `None` always passes (omitted keeps v1.0 defaults). Message payloads exactly: `limit must be between {MIN_LIMIT} and {MAX_LIMIT} (got {l})` and `ttl_secs must be between {MIN_TTL_SECS} and {MAX_TTL_SECS} (got {t})` (D-05).
- Error-tier mapping after this plan: REST `map_memory_error`: `InvalidType | InvalidQuery | InvalidArgument` → 400; MCP `map_mcp_error`: same three → `invalid_params`. Internal tier unchanged.
- Tag predicate shape (all three sites, D-07): `(?N IS NULL OR EXISTS (SELECT 1 FROM json_each(<table-or-alias>.tags) WHERE json_each.value = ?N))` — same parameter indices, same `params![]` bind lists, same NULL-disables-filter convention as the LIKE predicates they replace.
